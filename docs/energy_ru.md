# Энергодомен (Эпик 3C)

> Учёт потребления в кВт·ч по устройствам и зонам, деньги по тарифу и автоматический сдвиг откладываемых
> нагрузок в дешёвые часы. Всё построено поверх готовой телеметрии (Эпик 1B) и не требует внешней сети —
> статический тариф и оценка потребления работают офлайн.

## 1. Учёт kWh

Всё сводится к **единой кумулятивной серии `energy` (кВт·ч)** на устройство. Настраивается **в карточке
самого устройства** — вкладка «Настройки», секция «Энергопотребление». Источник значения — любой из трёх:

| Что умеет прибор | Как получается `energy` |
|---|---|
| Есть счётчик (`energy`) | публикуется прибором напрямую, настраивать нечего |
| Есть только мгновенная мощность `power` (Вт) | платформа интегрирует `∫ W·dt → кВт·ч` |
| Ничего не измеряет | мощность **оценивается** по состоянию и мощности из профиля, затем интегрируется |

**Потребление за период** считается на лету из телеметрии как сумма по-часовых приращений (`delta`) —
переиспользуется батч-агрегация `POST /api/telemetry/aggregate/batch` с `agg=delta` (см. `HistoryEndpoints`).
Сброс счётчика (перезагрузка устройства → счётчик обнулился) обрабатывается: приращение бакета с падением
значения читается как «счётчик перезапустился», отрицательного расхода не возникает.

**Защита от двойного счёта.** В энергопрофиле устройства есть роль:

- пусто / `consumer` — обычный потребитель, входит в суммы;
- `mains` — вводной/агрегирующий счётчик: показывается как «всего по вводу», но **исключён из суммы по
  устройствам** (иначе задвоение).

Совсем убрать прибор из учёта — это не роль, а **выключенный тумблер «Учитывать в потреблении»**.

## 2. Энергопрофиль устройства

Профиль (`PUT /api/capability-devices/{id}/energy-profile`) — единственное место, где задаётся мощность:

| Поле | Смысл |
|---|---|
| `track` | тумблер «Учитывать в потреблении»; пусто ⇒ по умолчанию (метрированный прибор учитывается, остальные — нет) |
| `role` | `consumer` (по умолчанию) / `mains` |
| `maxPowerW` | паспортная мощность при полной нагрузке |
| `minPowerW` | мощность на минимуме регулятора (нижний порог диммирования) |
| `standbyPowerW` | потребление в выключенном состоянии |
| `scaleCapabilityId` | регулятор (0..100 %): `brightness` / `fan_speed` / `position`; пусто ⇒ авто-выбор, иначе полная мощность при включении |
| `circuitId` | линия щита из схемы электросети (раздел 5) |

Оценка мощности линейна: выключено → `standbyPowerW`; включено с регулятором → `minPowerW + (maxPowerW −
minPowerW) × доля`; включено без регулятора → `maxPowerW`. Общий чистый калькулятор — `EnergyModel` в
контрактах, его же использует координатор нагрузки, поэтому «сколько даст сброс» и «сколько намотало»
считаются одинаково.

**Как это работает внутри.** `DeviceEnergyService` (AutomationService) раз в 30 с считает мощность каждого
отслеживаемого прибора и интегрирует её в кВт·ч, публикуя результат **от имени самого устройства**
(`DeviceStateReportV1`, источник `energy:{deviceId}`). Устройство при этом получает синтетические
capability `power`/`energy` — ровно те, которых у него нет, — поэтому тренды, правила, дашборд и майнеры
видят оценочный прибор так же, как метрированный. Особенности:

- накопитель сидируется из последнего известного `energy`, поэтому рестарт продолжает серию, а не обнуляет её;
- одиночный шаг интегрирования ограничен 1 часом — длинный простой не даёт ложный скачок;
- пока прибор `offline`, накопление на паузе: неизвестное состояние — это не нулевое потребление;
- публикация — при заметном изменении мощности или раз в 5 минут, поэтому телеметрия не захлёбывается;
- эти отчёты не влияют на «онлайн» устройства и не попадают в журнал активности (только в тренды).

Кнопка **«Взять измеренную»** подставляет в `maxPowerW` пик реальной мощности за последнюю неделю (агрегат
`max` по телеметрии) — удобно для розетки с ваттметром. При первом включении тумблера мощность
предзаполняется типовым значением по архетипу (лампа 9 Вт, конвектор 1000 Вт и т.п.) — это лишь подсказка.

## 3. Тариф

**Тарифная сущность** — виртуальное устройство `system/tariff` (`AdapterSource=System`, архетип `tariff`),
публикует раз в минуту `price` (текущая цена за кВт·ч) и `tariff_zone` (текущая зона). Цена числовая → идёт в
телеметрию как тренд; зона дискретная → в журнал как переходы. Устройство доступно правилам как любое другое.

**Модель тарифа** (`TariffSettings`, коллекция `tariff_settings`, чистый `TariffCalculator` в контракте):

| Поле | Что это |
|---|---|
| `currency` | метка валюты; единица цены = `{currency}/кВт·ч` |
| `defaultPrice` | цена, когда ни одна зона не подходит (одноставочный тариф) |
| `zones[]` | зоны: `{ name, pricePerKwh, intervals[] }` |
| `intervals[]` | локальные окна `{ startMinute, endMinute }` (минуты от полуночи) |

Правила вычисления: активна **первая** зона, чьё окно накрывает локальное время; зона без интервалов
активна всегда; если `endMinute ≤ startMinute`, окно переходит через полночь (ночной тариф 23:00→07:00).
Редактируется на `/settings` в секции «Тариф на электроэнергию»; офлайн-устойчиво.

**Деньги за период** — `GET /api/energy/cost`: сумма по-часового потребления потребителей × цена зоны,
активной в этот локальный час → общая стоимость + разбивка по зонам.

## 4. Блок «дешёвые часы»

Примитив 2Q **`cheap_hours`** сдвигает откладываемую нагрузку (бойлер, зарядка, полив) в самые дешёвые часы:

- читает вперёд-серию цен из тарифа (не привязка входа, а внутренний доступ к тарифу — как у солнечного
  блока к калькулятору солнца);
- параметры: `windowHours` (окно ранжирования), `cheapestHours` (сколько дешёвых часов работает),
  `maxPrice` (потолок цены, 0 = без ограничения); опция `plungeOnly` (только отрицательные цены);
- необязательный вход `enable` — гейт: при `false` принудительно выключает;
- выход `on_off` привязывается к нагрузке штатным путём актуации (Эпик 1D);
- решение фиксируется на локальный час (чтобы нагрузка работала целыми дешёвыми часами без дребезга).

## 5. Схема электросети (фазы, щиты, линии)

Настройки → **«Схема электросети»**. Дерево узлов, ортогональное зонам (одна линия обычно питает несколько
комнат, а комнату питают несколько линий):

| Тип узла | Что это |
|---|---|
| `supply` | ввод/источник: сеть, генератор, инвертор, солнце (можно связать с сигналом `power_source`) |
| `panel` | щит |
| `circuit` | линия — автомат, на котором висят устройства |

У узла задаются: родитель, **фаза** (`l1`/`l2`/`l3`/`three`; пусто ⇒ наследуется от родителя), **номинал
автомата** (А) и опциональный **счётчик узла** (любое устройство с `power`/`energy`). Устройство привязывается
к линии в своей карточке (поле «Линия щита»); фаза берётся от линии, трёхфазная линия раскладывается поровну
на L1/L2/L3.

**Что это даёт** (`GET /api/energy/breakdown`):

- потребление и текущая мощность **по линиям** и **по фазам** (перекос фаз виден сразу);
- **сведение баланса**: у линии со счётчиком показывается, сколько счётчик намерил и сколько из этого **не
  объяснено** известными приборами («неучтённое») — честный ответ для недоразмеченного дома;
- устройства без линии не подмешиваются в чужую линию, а выносятся отдельной суммой;
- лимиты по фазе и по линии для координатора нагрузки (см. `load_management_ru.md`): номинал автомата
  превращается в ватты (А × В, по умолчанию 230 В), явные лимиты задаются в «Управлении нагрузкой».

## 6. Энергодашборд

Тип элемента кастомного дашборда **«Энергия»** (`EnergyTile`, не привязан к устройству — как «Режимы»):

- тумблер периода 24ч / 7д / 30д;
- стоимость и кВт·ч за период;
- разбивка денег по тарифным зонам (если зон больше одной);
- переключатель **Устройства / Линии / Фазы** (появляется, когда описана схема электросети);
- рейтинг по выбранному разрезу + строка «Не отнесено к устройствам» (неучтённое + приборы без линии).

Данные — `GET /api/energy/consumption` + `/cost` + `/breakdown`. Потоки в стиле Sankey отложены.

## 7. API

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/energy/consumption?from=&to=&bucket=` | потребление по устройствам (кВт·ч) + суммы |
| `GET` | `/api/energy/cost?from=&to=` | деньги за период + разбивка по зонам |
| `GET` | `/api/energy/breakdown?from=&to=` | потребление по линиям и фазам + баланс/неучтённое |
| `PUT` | `/api/capability-devices/{id}/energy-profile` | энергопрофиль устройства (учёт, мощность, роль, линия) |
| `GET` `POST` `PUT` `DELETE` | `/api/power-topology` | узлы схемы электросети |
| `GET` `PUT` | `/api/settings/tariff` | тариф (валюта, базовая цена, зоны) |
| `GET` | `/api/telemetry/aggregate[/batch]` | агрегаты, добавлены `sum` и `delta` |

## 8. Миграция с Home Assistant

- Розетки/модули с измерением (`energy`/`power`) переносятся как есть — учёт начинается сразу.
- Аналог интеграции Powercalc — тумблер «Учитывать в потреблении» плюс мощность в карточке прибора (лампы по
  яркости, приборы по вкл/выкл). Отдельных сущностей-хелперов заводить не нужно.
- Тарифная сущность заменяет тарифные `sensor`-хелперы; RU много-тарифный (Т1/Т2/Т3) задаётся зонами.
- Механика «включи в N дешёвых часов» (в HA — из blueprints) — first-class блок `cheap_hours`.

## 9. Ограничения v1

- **Динамический почасовой тариф** (провайдер Nord Pool/Tibber-класса) — отложен: без реального провайдера не
  протестировать, статический много-тарифный закрывает RU-кейс. Тариф и блок «дешёвые часы» уже спроектированы
  под будущую вперёд-серию — провайдер добавится сверху без переделки.
- Оценка мощности линейная (`min..max` по регулятору); таблица точек (LUT) для нелинейных приборов —
  на будущее.
- Трёхфазный прибор раскладывается по фазам поровну: по-фазного измерения одной нагрузки нет.
- Потоки Sankey на дашборде отложены.
- Стоимость считается по устройствам-потребителям; при наличии вводного счётчика он показывается отдельно,
  но не подменяет сумму по устройствам.
