# Движок правил: ожидание событий, обязательные выражения, переменные, ветки ошибок (Эпик 3E)

> Расширяет детерминированный движок автоматизаций (Эпик 1A) четырьмя механиками, на которые упираются
> продвинутые пользователи: **ожидание события в середине действия** с таймаутом, **обязательное
> выражение** (живой гейт, отменяющий отложенные действия), **глобальные переменные** (именованные,
> переживают рестарт) и **ветки on-error**. Инвариант слоистости сохранён: безопасный пол (Эпик 1A) не
> троттлится и не гейтится пользовательскими выражениями — новые механики работают только над
> пользовательским слоем.

## 0. Где это в UI

Всё выражается в существующем **диалоговом редакторе правил** на `/automations` (визуальный flow-редактор
Эпика 1E был удалён — карта в этой части устарела; 3E работает поверх обобщённых `RuleEditors`).
Глобальные переменные — на отдельной странице `/variables`.

## 1. Ожидание события (`WaitForEvent`)

Новый тип действия `ActionType.WaitForEvent`: приостанавливает выполнение правила до совпадения состояния
устройства **или** таймаута.

- **Совпадение** — та же форма, что у триггера/условия: `waitDeviceId`/`waitZoneId` + `waitCapabilityId` +
  `waitOperator` (`eq|ne|gt|lt|gte|lte`) + `waitValue`. Реализовано **событийно** (не поллинг): ждущий
  подписывается на in-process `DeviceEventBroker`, куда `AutomationEngine` публикует каждое изменение
  capability. Если условие уже выполнено на момент входа в действие — проходит немедленно.
- **Таймаут** — `timeoutSeconds` (≤0 → 300 c по умолчанию, максимум сутки).
- **Ветка `onTimeout`** — список действий, выполняемый **только если** событие не пришло вовремя. Ветка
  **терминальна**: после неё основная последовательность действий не возобновляется. Пусто → таймаут
  просто «проваливается» без ветвления.

Пример: «включить свет → ждать `contact=open` двери ≤5 мин → иначе (ветка) отправить уведомление и
выключить свет».

## 2. Обязательное выражение (`RequiredExpression`)

Живой гейт (Hubitat «Required Expression»), в отличие от `Conditions` (проверяются один раз на входе):

- Должен выполняться **и чтобы правило стартовало** (складывается в `conditionsMet`), **и непрерывно пока
  оно выполняется**.
- Если во время выполнения (внутри `Delay` или `WaitForEvent`) выражение перестаёт быть истинным —
  отложенное действие **отменяется**. Механически: `RuleRunner` на время запуска подписывается на
  `DeviceEventBroker` и при каждом изменении переоценивает выражение; как только оно стало ложным —
  отменяет linked-`CancellationToken` запуска. `ActionExecutor` получает этот токен как любой другой, так
  что незавершённое ожидание разворачивается штатным путём `OperationCanceledException`. Отмена по гейту
  отличается от остановки хоста и пишется в историю как `cancelled: required expression no longer holds`.
- **Синтаксис**: условия — та же форма `RuleCondition` (device-state / time-of-day / sun / mode),
  ссылаются по индексу `C0`, `C1`, … и комбинируются `&&`, `||`, `!`, `( )`. Пустое выражение = **И** всех
  условий. Разбор — крошечный рекурсивно-нисходящий парсер (`RequiredExpressionEvaluator`); повторно
  используется `RuleEvaluator.ConditionHolds` (никакого нового языка значений). **Некорректное выражение
  fail-closed** (даёт `false`, а не пропускает правило без гейта).

Правила без гейта не затронуты: нет подписки, нет linked-токена — поведение идентично до-3E.

## 3. Глобальные переменные

Именованные постоянные значения, переживающие рестарт (Hubitat «Hub Variables»). Контракт
`GlobalVariable` (коллекция `variables`): `name`, `type` (`Number/Boolean/String/DateTime/List`),
`description`, `value`. Конфиг и значение — в одном документе (у переменной нет тика, против которого
дедуплицировать записи, поэтому отдельная `variable_state` не нужна — в отличие от `block_state` 2Q).

**Переменная как «устройство-коннектор».** `VariableRuntimeService` проецирует каждую переменную как её
собственное виртуальное capability-устройство (`DeviceIdFactory.Derive("Variable", id)`, единственная
writable capability `value`, тип по `VariableType`). Значит правила читают/пишут переменную **точно так
же, как любое устройство** — триггером, условием, обычным действием `Command`, привязкой порта
control-блока — без отдельного синтаксиса ссылок на переменные где-либо ещё. Запись durable: команда на
устройство переменной проходит через DbGateway (переживает рестарт), затем немедленно переопубликовывается.

- **API**: `GET/POST /api/variables`, `GET/PUT/DELETE /api/variables/{id}`, `PUT /api/variables/{id}/value`
  (только значение, не трогает имя/тип/описание) — проксируется ApiGateway → DbGateway.
- **UI**: страница `/variables` (список + CRUD-диалог, тип-зависимый редактор значения).

## 4. Ветки on-error

Каждое действие получает необязательную ветку `onError` (Homey «error card»): если действие выбрасывает
исключение во время выполнения — вместо аварийного прекращения всего запуска выполняются действия ветки.

- Ветка **терминальна** (после неё основная последовательность не возобновляется), запуск фиксируется как
  успешный с деталью `handled error: …` (не как ошибка).
- В сообщении `Notify` внутри ветки токен **`{error}`** подставляется текстом пойманного исключения
  («текст ошибки как контекст»).
- Действие **без** `onError` сохраняет прежнее поведение: необработанное исключение прекращает остаток
  запуска, запуск помечается неуспешным.
- Ветки (`onTimeout`, `onError`) ограничены **одним уровнем вложенности** — действие внутри ветки не
  показывает собственных веток (`nestable=false` в UI, рекурсия ограничена и в модели).

## Нормализация и персистентность

Все `object?`-значения новых полей (`RequiredExpression.Conditions[].Value`, `WaitValue`, значения внутри
`OnTimeout`/`OnError`) рекурсивно уплощаются из `JsonElement` в BCL-примитивы
(`AutomationEndpoints.NormalizeJsonValues` → `NormalizeAction`) перед записью в Mongo — иначе
`ObjectSerializer` отказывается их сохранять, как и для базовых полей правила (регрессия Эпика 2C).

  вложенные ветки), `RequiredExpressionEditor`, `Variables`, расширенный `safetyTemplates`.

## Границы v1

- Стек сброса переменных значений между рестартами: значение durable, но `VariableRuntimeService` не
  удаляет `capability_devices`-строку удалённой переменной (нет `DeviceRemovedV1` в шине) — приемлемый
  зазор v1.
- Живой docker-прогон (правило с WaitForEvent под реальным устройством, гейт-отмена под нагрузкой) —
  остаток до ✅ вместе с боевым развёртыванием.
