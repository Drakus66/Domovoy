# Бэкапы, восстановление и миграция (Эпик 3A)

> Полная резервная копия дома одним архивом: данные, настройки и настройки плагинов. Создание и
> восстановление доступны из UI (`/settings` → «Бэкапы») и по API. Восстановление возвращает дом к
> состоянию копии и перезапускает сервисы через шину (механика system-restart). Радиосеть Zigbee
> (координатор) в бандл не входит — у неё документированный отдельный трек (см. §5).

## 1. Что в бандле

Бандл — zip-архив `domovoy-backup-YYYYMMDD-HHmmss.zip` в каталоге бэкапов (в compose —
`./data/backups` на хосте):

| Внутри архива | Что это |
|---|---|
| `manifest.json` | версия формата, дата, БД, причина (`manual`/`scheduled`/`upload`), список коллекций с количеством документов и опциями time-series |
| `collections/{name}.bson` | все документы коллекции подряд в BSON (формат `.bson` mongodump — совместим с `bsondump`) |
| `plugin-settings/{id}.json` | настройки плагинов (Epic 1C, `{plugins-root}/.settings`) — если каталог примонтирован в db-gateway |
| `extras/{имя}/**` | дополнительные каталоги хоста из `Backup:IncludeDirectories` (опционально) |

Дампятся **все** пользовательские коллекции автоматически (устройства, зоны, правила, блоки и их
состояние, история, телеметрия, ML-модели с артефактами, ML-задачи, предложения, режимы, дашборды,
пользователи/роли, локация/календарь, дневник дома, настройки бэкапа). Новая коллекция в будущем
попадает в бандл сама — списка-перечня в коде нет.

**Не входит в бандл:**

- `ops_logs` — capped-коллекция оперативных логов (Serilog), это телеметрия эксплуатации, не состояние дома;
- радиосеть Zigbee — живёт в стике-координаторе и data-каталоге Zigbee2MQTT (§5);
- конфиги уровня хоста: `docker-compose.yml`, `.env`, каталог `plugins/` с бинарями плагинов —
  это deploy-каталог, он копируется при миграции как файлы (или подключается через `extras`, §6).

Time-series коллекции (`device_events`, `sensor_readings`) помечаются в манифесте своими опциями
(timeField/metaField/granularity) и при восстановлении пересоздаются именно как time-series —
вторичные индексы и TTL доедут при рестарте сервисов (`TimeSeriesInitializer` на старте
EventInterceptor).

## 2. Расписание и ретенция

Настраиваются на `/settings` → «Бэкапы» (хранятся в singleton-документе `backup_settings`):

- **Автоматический ежедневный бэкап** — вкл. по умолчанию: свежая установка сразу защищает себя;
- **Время** — в часовом поясе площадки (Epic 2K), без него — в поясе сервера;
- **Хранить копий** — после каждого успешного бэкапа старые копии сверх N удаляются.

Планировщик тикает раз в минуту; пропущенный слот (сервер был выключен) навёрстывается при первом
тике после включения. Ошибка бэкапа фиксируется в статусе («последний бэкап завершился ошибкой»)
и не ретраится до следующего суточного слота.

## 3. API

Все маршруты проксируются ApiGateway (`/api/backup/*` → DbGateway):

| Маршрут | Что делает |
|---|---|
| `GET/PUT /api/backup/settings` | расписание/ретенция + статус последнего запуска |
| `GET /api/backup` | список копий (манифест читается из архива; битые помечаются) |
| `POST /api/backup/run` | создать бэкап сейчас (409, если бэкап/восстановление уже идёт) |
| `GET /api/backup/{file}/download` | скачать архив (стримится, без буферизации) |
| `POST /api/backup/upload` | загрузить архив (сырое тело `application/zip`); файл валидируется и появляется в списке |
| `POST /api/backup/{file}/restore` | восстановить; `?restart=false` — не перезапускать стек (для тестов) |
| `DELETE /api/backup/{file}` | удалить копию |

## 4. Восстановление и миграция на новый хост

**Восстановление in-place** (тот же хост): `/settings` → «Бэкапы» → «Восстановить» у нужной копии.
Что происходит: коллекции из манифеста дропаются и пересоздаются из архива → настройки плагинов
пишутся обратно в `.settings` → по шине уходит `SystemControlV1(all, restart)` — все сервисы
корректно останавливаются, и docker-политика `restart: unless-stopped` поднимает их заново с
восстановленным состоянием. UI на минуту-другую теряет связь — это ожидаемо.

**Миграция на новый хост / восстановление на чистом стеке:**

1. на старом хосте: скачать свежий бандл («Скачать») — или взять файл из `./data/backups`;
2. на новом хосте: развернуть deploy-каталог (compose, `.env`, каталог `plugins/`), запустить стек
   (`docker compose up -d`) — БД поднимется пустой;
3. `/settings` → «Бэкапы» → «Загрузить архив» → у появившейся копии нажать «Восстановить»
   (альтернатива без UI: положить файл в `./data/backups` и вызвать restore по API);
4. стек перезапустится сам; проверить `/status` и `/devices`.

Zigbee-стик перетыкается в новый хост физически; его состояние — §5.

**Рекомендация:** восстановление выполняйте в спокойное окно (ночью/при минимуме событий): между
дропом и пересозданием time-series коллекции живой поток событий теоретически может неявно создать
обычную коллекцию; рестарт стека сразу после восстановления это чинит, но лучше не испытывать.

## 5. Zigbee-координатор — отдельный трек

Радио-сеть (ключи сети, таблица спаренных устройств) живёт в стике и обслуживается Zigbee2MQTT,
дампу из Mongo не подлежит:

- Z2M сам снимает бэкап координатора в `coordinator_backup.json` внутри своего data-каталога
  (в compose — `./data/zigbee2mqtt`). **Копируйте весь каталог `./data/zigbee2mqtt`** вместе с
  deploy-каталогом — там же `configuration.yaml` (сеть, `serial.port`) и `database.db` (устройства);
- миграция: перенести data-каталог + воткнуть тот же стик → устройства не переспариваются;
  восстановление на другой совместимый стик — процедура Z2M по `coordinator_backup.json`
  (см. документацию Z2M «Coordinator backup»);
- при желании каталог можно включить прямо в бандл через `extras` (§6) — но восстанавливается он
  только в staging (см. ниже), на место его кладут руками при выключенном z2m.

## 6. Extras: конфиги хоста в бандле (опционально)

`Backup:IncludeDirectories` (env `BACKUP__INCLUDEDIRECTORIES__0=...`) — список примонтированных в
db-gateway каталогов, которые архивируются в `extras/`. При восстановлении они **не** пишутся на
место: распаковываются в `./data/backups/restored-extras/{имя-бандла}/` для ручного разбора —
конфиги хоста нельзя молча перезаписывать под работающим стеком.

## 7. Конфигурация (env db-gateway)

| Ключ | Дефолт | Смысл |
|---|---|---|
| `BACKUP__DIRECTORY` | `backups` (в compose `/app/backups` → `./data/backups`) | куда писать бандлы |
| `BACKUP__PLUGINSETTINGSDIRECTORY` | пусто (в compose `/app/plugin-settings` → `./plugins/.settings`) | настройки плагинов в бандл/из бандла |
| `BACKUP__INCLUDEDIRECTORIES__N` | пусто | extras-каталоги (§6) |

Off-site бэкапы (шифрованная выгрузка наружу) — осознанно не в v1: локальная копия первична
(offline-first), off-site — опциональный слой позже (см. roadmap 3A).
