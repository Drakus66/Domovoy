# Сцены (Эпик 3B)

> Сцена — именованный снимок целевых состояний набора устройств. Включается одним касанием: из списка
> сцен, плиткой на дашборде или действием в правиле. Сцена — отдельная сущность (не автоматизация); она
> только группирует команды и активирует их штатным путём актуации (Эпик 1D). Редактирование сцены
> **никогда не трогает дом** — команды уходят только при явном включении.

## 1. Модель

Сцена (`scenes` в БД, контракт `Domovoy.Contracts.Scenes.Scene`):

| Поле | Что это |
|---|---|
| `id` / `name` / `description` | идентификатор (назначается сервером), название, необязательное описание |
| `targets[]` | список целей: `{ deviceId, set }`, где `set` — карта `capabilityId → значение` |

Значения `set` хранятся как обычные BSON-примитивы — на границе HTTP их нормализует
`SceneEndpoints.NormalizeJsonValues` (той же логикой, что и правила), поэтому повторное воспроизведение
как команды — чистый round-trip.

## 2. Создание и Re-Capture

Страница **«Сцены»** (`/scenes`):

- **Новая сцена** → диалог. Кнопка **«Снять с устройств»** (Re-Capture) открывает выбор устройств и
  снимает их **текущее** состояние в сцену. Снимаются только **управляемые** (writable) возможности —
  например, у термостата попадёт `temperature_setpoint`, а не read-only `temperature`.
- Значения затем свободно редактируются в диалоге (переключатель для булевых, выпадающий список для
  enum, поле для чисел/текста). Это редактирование **не применяется к дому** — только сохранение в БД.
- Устройство можно добавить повторным «Снять с устройств» — свежий снимок заменит прежнюю цель этого
  устройства.

## 3. Включение

Три равнозначных пути, все публикуют по одной `DeviceCommandV1` на каждое устройство цели с источником
`scene:{id}` (журнал атрибутирует изменение сцене):

1. **Кнопка «Включить»** в списке сцен → `POST /api/scenes/{id}/activate` (ApiGateway разворачивает цели
   в команды на шину; значения нормализуются к примитивам, как при ручном управлении).
2. **Плитка-сцена** на кастомном дашборде (тип элемента «Сцена») — включение одним касанием.
3. **Действие `scene`** в правиле (движок правил, Эпик 1A/1F): правило хранит только `sceneId`,
   `SceneStore` в AutomationService резолвит его в цели при срабатывании. Уважает стадии: в **Shadow**
   правило логирует «что бы включило», команд не шлёт.

## 4. API

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/scenes` | список сцен |
| `GET` | `/api/scenes/{id}` | одна сцена |
| `POST` | `/api/scenes` | создать |
| `PUT` | `/api/scenes/{id}` | заменить (редактирование без активации) |
| `DELETE` | `/api/scenes/{id}` | удалить |
| `POST` | `/api/scenes/{id}/activate` | включить (fan-out команд) |

CRUD проксируется в DbGateway; активация выполняется в ApiGateway (там есть шина).

## 5. Обнаружение сцен и расписаний (Эпик 2F × 3B)

Движок поиска закономерностей (`DiscoveryEngine`) сам замечает сцены — так же, как он предлагает правила, —
и кладёт кандидатов в очередь **«Предложения»** (`/proposals`). Как и везде, действует принцип 1: ничего не
создаётся без явного одобрения человеком.

**Обнаружение конфигураций → предложение сцены** (`SceneConfigurationMiner`). Движок реконструирует
состояние каждой зоны по журналу и ищет **аранжировки** — всплески **ручных** изменений нескольких
устройств зоны в пределах `SceneCoWindowSeconds`. Итоговое состояние зоны после всплеска — один экземпляр
конфигурации. Конфигурация, которую собирали вручную ≥ `SceneMinSupport` раз на ≥ `SceneMinDevices`
устройствах, предлагается как сцена (`ProposalKind.Scene`). Анти-loop: всплеск начинают/продолжают **только
пользовательские** касания — изменения от сцены/правила/ML/блока никогда, поэтому движок не «переоткрывает»
собственный вывод. Конфигурация, уже сохранённая как сцена (тот же набор включённых устройств), пропускается.

**Обнаружение расписания.** Если экземпляры конфигурации ещё и **кучкуются по времени суток** (разброс ≤
`SceneScheduleMaxSpreadMinutes`), предложение несёт ежедневный cron: при одобрении создаётся не только сцена,
но и активное правило, включающее её в это время.

**Обнаружение включений готовой сцены → предложение правила** (`SceneActivationMiner`). После того как сцена
существует, движок следит, как её включают. Активация публикуется с источником `scene:{id}`, который журнал
атрибутирует отдельно (`TriggerSources.Scene`, `TriggerId` = id сцены), поэтому ручное нажатие плитки
отличимо от уже автоматизированного срабатывания правила. Если сцену включают вручную ≥
`SceneScheduleMinSupport` раз около одного времени, движок предлагает `Proposed`-правило с действием `scene`
(триггер по времени). Одобрение переводит правило в `Active` — обычный путь одобрения правил (с проверкой
через «Симуляцию», Эпик 1F).

Одобрение Scene-предложения материализует сцену в коллекции `scenes` (`ProposalApplication.ApplySceneAsync`);
до одобрения сцены не существует — она не появляется в `/scenes` и на дашбордах преждевременно.

Пороги настраиваются в секции `Automation` (`SceneStateCapabilities`, `SceneQuantizeSteps`,
`SceneCoWindowSeconds`, `SceneMinDevices`, `SceneMinSupport`, `SceneScheduleMinSupport`,
`SceneScheduleMaxSpreadMinutes`).

## 6. Ограничения v1

- Переходы (fade) не реализованы — сцена задаёт целевые значения мгновенно.
- Значения сцены — снимок на момент захвата/редактирования; сцена не «отслеживает» устройство.
- Живой прогон в docker-стеке не выполнялся (покрытие — интеграционные тесты на реальном Mongo +
  тесты WebUI).
