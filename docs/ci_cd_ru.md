# Поставка и обновления (Эпик 3K)

Как коммит превращается в версию, работающую дома, и как дом обновляется кнопкой в интерфейсе,
а не по SSH.

Цепочка целиком:

```
коммит → тесты (гейт) → селективная сборка образов → реестр (GHCR)
                                                        ↓
                       уведомление в доме ← служба обновлений следит за каналом
                                                        ↓
                     /settings → «Обновить» → бэкап → pull по digest → docker compose
```

## 2. Каналы и версии

Канал определяется веткой:

| Ветка | Канал | Теги образа |
|---|---|---|
| `develop` | `dev` | `1.4.57-dev`, `dev`, `sha-ab12cd3` |
| `master` | `release` | `1.4.57`, `release`, `sha-ab12cd3` |

`MAJOR.MINOR` каждого компонента задаётся вручную в `build/components.json`, `PATCH` подставляет CI
из номера прогона. Версия монотонна по построению, поэтому тег не может быть перезаписан.

**Бандл топологии версионируется по тем же правилам:** `MAJOR` — версия топологии из
`build/components.json`, `MINOR` — `0`, `PATCH` — номер прогона (`3.0.57-dev`). Формат тега — часть
контракта с домом: служба обновлений отбирает теги регуляркой `^\d+\.\d+\.\d+(-dev)?$` и по суффиксу
отделяет канал (`RegistryClient.IsChannelVersionTag`). Пакет с тегом вне этого формата дом просто не
видит — молча, как отсутствующий в канале. Ровно так бандл, публиковавшийся под тегом `3.4`, и пропал:
первое же обновление отказывало фразой «`connectivity-service` требует интерфейс `topology`, которого
никто не предоставляет». Обе стороны шва держит тест `ReleaseTagFormatTests`.

Локально собранный образ остаётся на версии `0.0.0` (дефолт `ARG VERSION` в Dockerfile) — это
намеренный признак «собрано здесь, а не пришло из канала».

**Как бампнуть минорную версию:** поднять `version` компонента в `build/components.json` в PR.
Отдельного релизного ритуала нет.

## 3. Селективная сборка

Пересобираются только компоненты, чьи пути затронул диапазон коммитов:

- правка `src/Services/Domovoy.AutomationService/**` → один образ;
- правка `src/Common/Domovoy.Contracts/**` → **все .NET-компоненты** (контракты вкомпилированы в
  каждый из них);
- правка `docker-compose.yml` → бандл топологии;
- правка `src/UI/WebUI/**` → только webui;
- правка `src/Plugins/**` → образ `plugin-supervisor` (см. ниже).

Непересобранный компонент просто остаётся в реестре с прежней версией, а подвижный тег канала
продолжает указывать на старый образ. Это и делает возможным точечное обновление на стороне дома.

**Плагины едут внутри образа супервизора.** Плагин — это папка на томе хоста (`./plugins`), а не
compose-сервис, поэтому отдельным компонентом реестра он быть не может: у него нет ни контейнера, ни
образа, который можно было бы пересоздать. Первопартийные плагины публикуются в
`/app/builtin-plugins/<id>` внутри образа `plugin-supervisor` (его `Dockerfile`), а супервизор на
старте раскладывает их в plugins-root
([`BuiltInPluginSeeder`](../src/Services/Domovoy.PluginSupervisor/Plugins/BuiltInPluginSeeder.cs)).
Правило раскладки уважает удаление владельцем: раскладываем, если плагина ещё ни разу не было или
образ несёт версию новее установленной; если владелец удалил плагин из UI — не воскрешаем. Плагин,
установленный владельцем через загрузку zip, к первопартийным не относится и не трогается.

`src/Tools/**` (эмулятор устройств) намеренно не принадлежит ни одному компоненту: это локальный
инструмент разработчика, в docker его нет и каналом обновлений ему ехать некуда.

Проверить локально, что и почему соберётся:

```bash
git diff --name-only HEAD~1 HEAD > /tmp/changed.txt
node build/tools/plan-build.mjs --changed /tmp/changed.txt --channel dev --run 0 --sha $(git rev-parse HEAD)
```

## 4. Модель совместимости

Правила, что и когда поднимать, — раздел «Контракты и совместимость» в
[`architecture/coding_standards_ru.md`](architecture/coding_standards_ru.md). Здесь — устройство.

Каждый образ несёт метку `ru.domovoy.deps`:

```json
{
  "component": "automation-service",
  "version": "1.4.57",
  "bus":      { "speaks": 3, "understands": 2 },
  "provides": { "automation-api": { "version": 3, "minCompat": 2 } },
  "requires": { "db-api": 4, "topology": 5 }
}
```

Три вида ограничений:

**`provides`/`requires` — точечные.** Провайдер держит диапазон `[minCompat, version]`; потребитель,
требующий `R`, удовлетворён при `minCompat ≤ R ≤ version`. Зависимость всегда на **интерфейс**, а не
на сервис: у интерфейса ровно один провайдер, поэтому произвольные циклы не возникают.

**`bus` — общая шина.** Провайдера нет: `Domovoy.Contracts` живёт в каждом образе. Набор совместим
при `max(understands) ≤ min(speaks)`. Отсюда важное следствие: ломающее изменение контрактов
поднимает `understands`, и решатель **сам** приходит к «обновить всё». Полное обновление — не
отдельный режим, а вывод.

**`topology` — обычная зависимость.** Бандл compose участвует в решателе как ещё один компонент.
Сервису, которому нужна новая переменная окружения, достаточно написать `requires: {"topology": 6}`
— решатель поставит обновление топологии раньше него. Никакого «требуется ручное обновление».

### Циклы — не тупик

Взаимные требования означают, что промежуточное состояние несовместимо, то есть компоненты должны
двигаться **вместе**. Решатель находит такие множества алгоритмом Тарьяна (сильно связные компоненты)
и исполняет их одной атомарной группой. Единственный настоящий отказ — «в канале нет набора версий,
удовлетворяющего ограничениям», и он всегда называет конфликтующую пару.

## 5. Топология: кому принадлежит compose

Разделение владения — как `/usr` и `/etc` в дистрибутивах Linux:

```
/opt/domovoy/
  releases/topology-6/docker-compose.yml   ← НАШЕ, приезжает с релизом, read-only
  current -> releases/topology-6           ← симлинк; откат = переключить обратно
  docker-compose.override.yml              ← ВЛАДЕЛЬЦА, обновлением не трогается
  .env                                     ← ВЛАДЕЛЬЦА, только долив новых ключей
  state/pinned.yml                         ← пины digest'ов, генерирует служба обновлений
  data/…                                   ← тома
```

Запуск:

```bash
docker compose --project-directory /opt/domovoy \
  -f current/docker-compose.yml -f docker-compose.override.yml -f state/pinned.yml \
  --env-file .env up -d
```

`--project-directory` обязателен: без него относительные пути (`./data`, `./plugins`) уехали бы
внутрь каталога релиза, и дом поднялся бы с пустым состоянием.

**`state/pinned.yml` — то, без чего точечность невозможна.** Стоковый compose ссылается на подвижный
тег канала, поэтому голый `up -d` утащил бы все сервисы на свежие сборки. Служба обновлений пиннит
каждый сервис по digest; обновить один компонент — значит поменять один digest и поднять один сервис.

**`.env` доливается, не перезаписывается.** Из `.env.template` добавляются только отсутствующие ключи
(вместе с комментарием над ними). Пароль, путь к стику или домен, которые задал владелец, неприкосновенны.

**Миграции топологии** объявляются в `build/topology/manifest.json` декларативным набором:
`create-dir`, `rename-volume`, `remove-service`, `exec-in-service`. Произвольный shell не поддержан
намеренно — миграция на чужом доме обязана быть предсказуемой.

## 6. Как устроено применение

1. **Preflight** — доверие к источнику, доступность Docker, свободное место.
2. **Бэкап** (`POST /api/backups/run?reason=pre-update`). В манифест бэкапа попадают версии и
   digest'ы всех компонентов — «восстановить как было» остаётся осмысленным.
3. **Топология**, если она в плане: скачать бандл, долить `.env`, прогнать миграции, переключить симлинк.
4. **Pull по digest** только тех компонентов, что в плане.
5. **Пересоздание по группам** решателя: обновить пины → `docker compose up -d --no-deps <сервисы>`.
   Атомарная группа поднимается одной командой. Провал → возврат прежних пинов.
6. **Самообновление последним.** Контейнер не может пересоздать сам себя: как только его остановят,
   остановится и код, который этим занимается. Поэтому финальный шаг запускает одноразовый контейнер
   из **нового** образа службы обновлений, который дожидается смерти предшественника и поднимает его
   заново. Тот же приём использует watchtower.

Прогресс пишется в `state/current-run.json` на хосте, а не держится в памяти: api-gateway и WebUI
пересоздаются ближе к концу, браузер **обязательно** потеряет соединение, и после переподключения
страница должна дочитать, чем всё кончилось.

## 7. Доверие к источнику

Реестр и имена пакетов — **константы в коде** (`ReleaseSource.cs`), а не настройка: ни переменной
окружения, ни поля в интерфейсе. Настраивается только канал. Образы адресуются **по digest**,
подвижный тег используется лишь чтобы узнать, на какой digest он сейчас указывает.

Честный объём: это защищает от случайности и кривой настройки. От компрометации GHCR-аккаунта и от
форка, который поправил одну строку и пересобрал, — не защищает, и не должно: AGPL прямо разрешает
форк, и форк обязан поставляться из своего канала. Задача в другом — чтобы **этой** установке нельзя
было подсунуть чужой образ.

Криптографическую границу проводит подписанный релиз-манифест: CI подписывает список версий и
digest'ов ключом Ed25519, служба обновлений проверяет его вшитым публичным ключом. Шов под это уже
стоит — интерфейс `IReleaseTrustPolicy`; сегодня в нём реализация `ConstantSourceTrustPolicy`,
подписанная станет второй, без правок вокруг.

## 8. Гейты в CI

| Job | Что проверяет |
|---|---|
| `contract-guard` | Контрактные пути тронуты — значит `build/components.json` должен быть изменён, либо коммит несёт строку `Compat: none`. Контрактными считаются `Domovoy.Contracts`, `Endpoints/`, `Controllers/`, `docker-compose.yml` и манифесты плагинов `src/Plugins/*/plugin.json` |
| `validate-components` | Интерфейс без провайдера, `requires` вне диапазона, расхождение по версии шины |
| `build-test` | Сборка решения + офлайн-юнит-тесты **всего решения** (.NET и WebUI) |
| `offline-smoke` | Инвариант offline-first на реальных RabbitMQ + Mongo (Testcontainers) |
| `ContractsPublicApiTests` | Снимок публичной поверхности `Domovoy.Contracts` — любое изменение видно в диффе; отсутствие снимка — падение, а не тихое создание |
| `ReleaseSourceTests` | Список компонентов в `build/components.json` и в `ReleaseSource.Components` не разошёлся, порядок пересоздания цел (updater последним), у каждого объявленного компонента есть Dockerfile |

> **Где какой workflow срабатывает.** `release.yml` — на `develop` и `master`; тесты он вызывает
> из `ci.yml` через `workflow_call`. Поэтому у самого `ci.yml` в push-триггерах остались только
> `epic-*` и pull request: держать там `develop`/`master` значило бы прогонять весь набор тестов
> дважды на каждый пуш.

> Тестовые шаги адресуют `Domovoy.sln`, а не отдельный `.csproj`. Указание конкретного проекта уже
> однажды привело к тому, что тесты `Domovoy.CommutePlugin.Tests` не выполнялись в CI ни разу, —
> а `Domovoy.IntegrationTests` вообще не входил в решение и не собирался гейтом сборки.

Проверить контракт локально перед коммитом:

```bash
bash build/tools/contract-guard.sh HEAD~1 HEAD
node build/tools/validate-components.mjs
```

Переутвердить снимок после осознанного изменения контрактов:

```bash
UPDATE_APPROVALS=1 dotnet test --filter ContractsPublicApi
```

Все случаи, когда совместимость подтверждали вручную:

```bash
git log --grep='^Compat: none'
```

## 9. Локальная разработка — что изменилось

Почти ничего. Корневой `docker-compose.yml` остался прежним по формату, поэтому работают как
работали: запуск из Visual Studio (`docker-compose.dcproj`), `start-domovoy.bat`,
`docker compose up -d`, `docker-compose.override.yml`, локальный `.env`.

Боевой compose **не хранится второй копией** — он генерируется из корневого в CI. Ручная копия
неминуемо разъехалась бы с оригиналом.

Изменилось три вещи:

1. **Дисциплина `build/components.json`** — см. раздел 4 и стандарты кода.
2. **В стеке появился `domovoy-updater`.** В `docker-compose.override.yml` ему выключена проверка
   обновлений: никто не хочет получать «доступна новая версия», пока сам эти версии и делает.
3. **Версия локального образа — `0.0.0`** вместо прежнего `1.0.0`.

## 10. Что осталось за контуром

- **Docker Engine, ОС и systemd не обновляются.** Служба обновлений живёт в контейнере и обновляет
  Domovoy целиком, включая топологию, но не платформу под собой. Полное покрытие требует нативного
  хост-агента — сознательно отложено.
- **Семантическое изменение без изменения сигнатуры** ни один гейт не поймает: тот же эндпоинт, тот
  же тип, другой смысл поля. Это на код-ревью.
- **Пользовательский `docker-compose.override.yml` может конфликтовать** с новой топологией. Тогда
  `up -d` падает, служба возвращает прежние пины и симлинк, а вывод compose показывается в интерфейсе.
- Инфра-образы (`mongo`, `rabbitmq`, `zigbee2mqtt`) авто-обновлению **не подлежат** и обновляются
  отдельно.
- Кто контролирует хост, всегда может запустить `docker compose` с любым образом. Защищается канал
  поставки, а не машина.
