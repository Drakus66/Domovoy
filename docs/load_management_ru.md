# Управление нагрузкой (Эпик 3C-LM)

> Надстройка над энергодоменом (Эпик 3C): в дорогой час или при переходе на автономное питание
> (батарея/солнце, сеть пропала) ограничивает суммарную мощность дома и сбрасывает некритические
> потребители по приоритету. Мягкий интерлок — без гейтинга команд, только реакция постфактум и
> уведомление. **Выключено по умолчанию**: пустой список бюджетов = ничего не делает, даже если
> глобальный тумблер включён.

## 1. Сигнал `power_source`

Виртуальное устройство **`system/power`** (`AdapterSource=System`, рядом с `system/home`/`system/tariff`)
публикует writable enum-capability `power_source`: `grid` / `grid_peak` / `battery` / `solar` / `off`.
Значение живёт **только в памяти AutomationService** (не персистится через DbGateway, в отличие от
режима дома) — дефолт после рестарта всегда `grid`. Меняется, как и любая другая capability, командой
(`PUT /api/device-control/{id}/set` с `power_source`, либо действием правила) — обычно правило-мост от
реального ИБП/инвертора, либо ручной оверрайд для теста.

## 2. Бюджеты (`/settings` → «Управление нагрузкой»)

`LoadManagementSettings` (коллекция `load_management_settings`, синглтон):

| Поле | Что это |
|---|---|
| `enabled` | глобальный тумблер; `false` → координатор не делает вообще ничего |
| `budgets[]` | `{ powerSource, limitWatts }` — лимит мощности (Вт) для каждого источника; нет записи для текущего сигнала = без лимита |
| `phaseLimits[]` | `{ phase, limitWatts }` — лимит по фазе (L1/L2/L3); пусто ⇒ берётся номинал вводного автомата из схемы электросети |
| `circuitLimits[]` | `{ circuitId, limitWatts }` — переопределение лимита линии; по умолчанию действует номинал её автомата |
| `restoreMarginWatts` | запас (Вт) ниже бюджета, необходимый перед восстановлением — гистерезис против дребезга |
| `minDwellSeconds` | минимальная выдержка перед тем, как действие можно откатить |

## 3. Профиль нагрузки (дровер устройства → «Управление нагрузкой»)

Показывается только для устройств с writable `on_off` (это capability, которое координатор всегда
использует для полного отключения). `LoadSheddingProfile` — поле `loadShedding` на документе устройства:

| Поле | Назначение |
|---|---|
| `enabled` | опт-ин — без этого устройство не трогается, даже если тумблер режима говорит «sheddable» |
| `protected` | никогда не сбрасывается, независимо от режима (антизамерзание, CO₂, дым и т.п.) |
| мощность | берётся из **энергопрофиля устройства** (`maxPowerW`, см. `energy_ru.md`) — единственное место, где задаются ватты |
| `curtailable` + `controlCapabilityId` | можно ли и через какую числовую capability **снижать** (не выключать) — например `brightness` |
| `curtailedValue` / `restoreValue` | что командовать при снижении / при возврате |
| мощность в сниженном режиме | вычисляется по той же линейной модели из `curtailedValue` — если снижаемая capability не является регулятором мощности устройства, экономия неизвестна и нагрузка сразу выключается |
| `modeTier[mode]` | `critical` (никогда не сбрасывать в этом режиме) \| `sheddable` (можно, см. приоритет) \| `unmanaged` (не участвует; дефолт для незаданных режимов) |
| `modePriority[mode]` | приоритет сброса при `sheddable` — меньше номер, раньше сбрасывается |

Матрица режимов в UI — 4 известных режима (Home/Away/Night/Vacation); заводит их пользователь сам,
никакой встроенной логики «что критично» нет.

## 4. Алгоритм координатора `LoadManager`

Событийный сервис в AutomationService (реагирует на отчёты `power`, не на медленный тик):

0. **Области контроля.** Одновременно проверяются: **дом** (бюджет текущего `power_source`), каждая **фаза**
   с лимитом и каждая **линия** с номиналом автомата (из схемы электросети, см. `energy_ru.md`). Если схема
   не описана, остаётся ровно один домовой бюджет — поведение как раньше.
1. **Измерение.** Дом: мощность вводного счётчика (роль `mains`, если есть), иначе сумма `power` по
   учитываемым устройствам. Фаза/линия: счётчик соответствующего узла, если он задан, иначе сумма `power`
   приборов на этой фазе/линии (трёхфазная линия даёт треть в каждую фазу).
2. **Сброс** (что-то превысило свой лимит — начиная с самой «тесной» области): кандидаты — включённые, не
   `protected`, `sheddable` в текущем режиме и **принадлежащие этой области**, отсортированы по приоритету
   (меньше — раньше), при равенстве — по большей мощности.
   - Фаза 1 — **снижение**: для кандидатов с известной оценкой сниженной мощности командуется `curtailedValue`.
   - Фаза 2 — **отключение**: `on_off=false` для всех, кто ещё не выключен (включая уже сниженных, если
     снижения не хватило).
   - Останавливается, как только оценочная мощность опускается до лимита; кандидатов с более низким
     приоритетом не трогает.
3. **Восстановление** (ни одна область не превышена): пока верхняя запись стека сброса отстояла
   `minDwellSeconds` и её возврат не съедает запас **в самой тесной из её областей** — восстанавливает
   **в строго обратном порядке** (LIFO), не перескакивая через ещё не готовую запись.
4. **Нехватка мощности.** Если после исчерпания кандидатов бюджет всё равно превышен — отдельное
   уведомление (дебаунс ≥5 мин, чтобы не спамить).

Инвариант безопасности: `protected` и tier≠`sheddable` проверяются в самом фильтре кандидатов — сервис
физически не может отправить команду устройству вне этого списка. Это пользовательский слой **над**
безопасным полом (принцип 1) — правила/блоки антизамерзания и т.п. не зависят от координатора и не
гейтятся им.

## 5. Уведомления

Через существующий `NotificationDispatcher` (Эпик 2G/2M.2 LAN-канал): предупреждение при снижении/
отключении («превышен бюджет N Вт»), информационное при восстановлении, предупреждение при нехватке
управляемых нагрузок.

## 6. API

| Метод | Путь | Назначение |
|---|---|---|
| `GET` `PUT` | `/api/settings/load-management` | глобальные настройки (тумблер, бюджеты, лимиты фаз/линий, запас, выдержка) |
| `PUT` | `/api/capability-devices/{id}/load-shedding` | профиль устройства (`null` — сбросить, устройство становится unmanaged) |

## 7. Ограничения v1

- Стек сброшенных действий **только в памяти** — не переживает рестарт AutomationService. При реальном
  превышении бюджета следующий же отчёт о мощности пересоберёт сброс с нуля; после рестарта возможен
  короткий момент превышения до первого отчёта.
- `power_source` не персистится — то же самое, дефолт `grid` после рестарта.
- Снижение — команда заранее заданного значения (`curtailedValue`), не адаптивное регулирование.
- Матрица режимов в UI — только 4 известных режима; кастомные режимы дефолтятся к `unmanaged`.
- Аппаратный интерлок (защита от одновременного пуска нескольких мощных нагрузок на уровне тока) —
  вне рамок; это программный сброс постфактум, не гарантирует защиту от броска пускового тока.
