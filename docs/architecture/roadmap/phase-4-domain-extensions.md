# Фаза 4 — Домен-расширения (среднесрочно)

**Цель фазы:** расширить продукт **вширь** — новые домены (охрана, свет, энергия-аналитика, сеть, план дома) и каналы
поверх зрелого ядра Фазы 3 (Приоритет-2 исследования). Часть доменов требует полной авторизации (Фаза 5) для жёсткого
enforcement — здесь строим **модель/данные/UX**, критичное исполнение (PIN, замки) ждёт auth.

С 2026-07-22 фаза несёт и **программу «Голоса ML»** (решение №10; UX-волна 1 — эпики 3I/3J Фазы 3): сначала
субстраты — ритм дома (4I), страж/наблюдения + time-series (4J), погода (4K); затем флагманы — тепловой автопилот
(4L), денежный советник (4M), энергоподпись (4D на субстрате 4J), адаптивный свет на коррекциях (4C этап 2);
затем глубина — лаборатория гипотез и «что-если» (4N).

### Эпик 4A. Иерархия локаций (дом→этаж→комната) как адресуемая семантика ⬜

> **openHAB semantic model** (Location → Equipment → Point + Property): питает авто-дашборды по комнатам, правила-мишени
> («весь свет на кухне»), будущий голос (Фаза 5, «выключи свет на кухне» резолвится семантикой). У нас есть Zone-граф
> (P0-3, `ParentZoneId` + `Zone.Kind`) — но **адресация «все X в Y»** и семантические роли отсутствуют. Стыкуется с
> zone-scoping ML-шаблонов (2I).

- Расширить Zone семантическими ролями поверх готового графа; **адресация по (зона × архетип/capability)** → «все
  `light` в `kitchen`» для правил/сцен/дашбордов; авто-дашборд по комнате из семантики (HA Areas-дашборд 2025.4).
  Голос-резолюция — задел под Фазу 5.
- **DoD:** адресация «все <архетип> в <зоне>» доступна правилам/сценам/дашбордам; иерархия дом→этаж→комната отражена;
  авто-дашборд по комнате строится из семантики; готов hook под голосовую резолюцию.

### Эпик 4B. Охранный домен (Alarmo/HSM-модель) ⬜ (enforcement — Фаза 5)

> **Alarmo** (референс поверх HA) / Hubitat **HSM**: areas + зоны сенсоров, до 5 arm-режимов с индивидуальным
> периметром, exit/entry delay + trigger time, PIN-пользователи. **Страховой аргумент:** скидки 3–5% за датчики,
> **7–10% за авто-отсечку**. Режимы 1G + роли 2E + watchdog-культура уже есть; датчик+кран — Zigbee, работает через Z2M.

- **Arm-режимы** (до 5) поверх Home/Away/Night/Vacation с per-state периметром сенсоров; каналы **вторжение/протечка/дым**;
  entry/exit/trigger delays; тайл arm/disarm; per-mode таблица реакций. **Готовый архетип-паттерн «протечка → кран»**
  (Aqara Water Leak T1 ~$15 + Valve Controller T1 на шаровый кран, Zigbee) → реакция **<2 c локально**. **PIN-пользователи
  и enforcement** (кто может arm/disarm) — модель готовим, жёсткое исполнение = Фаза 5 (auth поверх ролей 2E).
- **DoD:** настраивается ≥2 arm-режима с периметром сенсоров; протечка → закрытие крана срабатывает <2 c локально;
  тайл arm/disarm; PIN/enforcement помечены под Фазу 5 (модель — готова).

### Эпик 4C. Циркадное освещение как свойство лампы (Adaptive Lighting) ⬜

> **Apple Adaptive Lighting:** циркадная температура — **свойство лампы, не правило**: включил любым способом —
> температура уже правильная. Ежедневно заметный эффект; солнечный виртуальный сенсор (NOAA, 2L) уже есть.

- **«Перехватчик включения»:** событие `off→on` лампы с `color_temp` → мгновенная установка по циркадной кривой (на
  базе Sun 2L / времени). Реализация — control-block (2Q) + перехват on-события, кривая настраивается. Работает офлайн.
- **Этап 2 (после 3J, программа «Голоса ML»):** персонализация кривой обучением на ручных коррекциях — сигнал
  вмешательств 3J превращает поправки жильца (яркость/температура после автоустановки) в смещение кривой; ML-форма —
  через шаблоны 2I.
- **DoD:** включённая любым способом лампа получает циркадную `color_temp` мгновенно; кривая настраивается; офлайн.

### Эпик 4D. ML энерго-аномалии (standby/«вампиры»/нетипичное → 2C) ⬜

> В self-hosted мире **не автоматизировано никем** (у HA/Homey/Hubitat — нет); академический мейнстрим (Isolation
> Forest, автоэнкодеры). `ml_tasks` (2P) + discovery (2F) + энергодомен (3C) превращаются в **видимую уникальную
> ценность**. Инвариант учителя тот же — не ML-on-ML.

- Поверх энергодомена 3C и воронки 2F — детектор аномалий потребления (standby-вампиры, нетипичные всплески/паттерны)
  на ML.NET (time-series/baseline-субстрат — эпик 4J) → предложение в очередь **2C** с обоснованием; апрув и стадийный
  выкат — те же (принцип 1).
- **DoD:** детектор находит standby-вампир/аномалию на истории потребления и кладёт предложение в 2C с метриками;
  активация только через апрув очереди.

### Эпик 4E. Карта топологии сети в UI (Zigbee → позже Thread/Matter) ⬜

> Hubitat (встроенные карты Z-Wave/Zigbee + health + ремонт из UI) и HA Matter Server 9.0 задали планку. Продолжение
> нашей liveness-watchdog культуры (device-liveness).

- Топология Zigbee из Z2M (граф маршрутизации + LQI/health) → визуализация (reactflow, как block-graph 1E) + health-
  статусы + ремонт/переспаривание из UI. Позже — Thread/Matter (Фаза 5).
- **DoD:** экран показывает граф Zigbee-сети с health-статусами; проблемные/слабые узлы видны; заложен hook под
  Thread/Matter-топологию.

### Эпик 4F. Community-канал шаблонов (rule/composite templates + shareable URL/QR) ⬜

> **openHAB marketplace** («форум = магазин», без тяжёлой инфраструктуры; Rule Templates с мастером параметров) +
> **SmartThings Shareable Routines** (автоматизация → URL/QR, установка в один клик). Галерея AddBlockPicker (2Q) и
> zip-плагины (1C) уже есть — **не хватает внешнего канала обмена**.

- Параметризуемые rule/composite-шаблоны (2Q-шаблоны + DSL `param` уже есть) → экспорт/импорт как **URL/QR**
  (SmartThings-стиль) + мастер запроса параметров (openHAB) + опциональный форум/каталог. Галерея расширяется внешними
  шаблонами.
- **DoD:** шаблон правила/композита упаковывается в переносимый URL/QR и ставится в один клик с запросом параметров;
  внешний шаблон появляется в галерее.

### Эпик 4G. План дома как тип дашборда (пины устройств на поэтажном плане) ⬜

> **Alexa Map View** (LiDAR-скан → поэтажный план с пинами, управление тапом по месту). **Ручная загрузка плана
> покрывает 90% ценности без LiDAR** — тип вкладки в существующие custom-dashboards.

- Новый тип элемента/вкладки в custom-dashboards (Mongo `dashboards`): загруженное изображение плана + пины устройств
  (позиция) + этажи слоями; управление тапом по месту (штатный actuation-путь).
- **DoD:** пользователь грузит план, расставляет пины устройств, управляет тапом по месту; этажи переключаются слоями.

### Эпик 4H. Persistence-фильтры телеметрии + restoreOnStartup ⬜ (малый)

> **openHAB** per-item strategies (everyChange/threshold/time-filter/restoreOnStartup). Снижает шум телеметрии,
> повышает выживаемость состояния. Частично уже есть (`block_state` 2Q, TTL 1B) — обобщаем per-signal.

- Per-signal стратегия записи (everyChange / порог / time-filter) в `EventInterceptor`/телеметрии (1B);
  restoreOnStartup-семантика для виртуальных/writable состояний (расширение `block_state`).
- **DoD:** сигнал можно писать по порогу/времени, а не на каждый семпл; выбранное состояние восстанавливается на старте.

## Программа «Голоса ML» (решение №10) — субстраты, флагманы, глубина

> Продолжение волны 1 (3I «Тишина и пульс» + 3J «Вмешательства и живые правила»). Рамка: каждая ML-фича говорит
> одним из четырёх «голосов» — **«сделал за тебя»** (автопилоты: молча, с ответом на «почему»), **«я заметил»**
> (страж: наблюдение с кнопкой «это норма»), **«я предлагаю»** (советник: только очередь 2C с памятью отказов),
> **«исследуй со мной»** (лаборатория: только по запросу). Порядок ниже — по зависимостям: 4I/4J/4K — субстраты,
> 4L/4M (+4D, 4C-этап 2) — флагманы поверх них, 4N — глубина.

### Эпик 4I. «Ритм дома» — модель суточного профиля как субстрат ⬜

> Одна модель вместо десятка частных: вероятностный профиль дома (спит/пуст/активен; типичные времена
> подъёма/ухода/возвращения/отбоя по дню недели и сезону) поверх готового event-log/телеметрии. Субстрат для всех
> трёх «голосов»: автопилоты («греть к возвращению»), страж («движение в необычное время»), советник («вы
> возвращаетесь к 18:40 — подогревать к приходу?»). Закрывает presence-фичу ML-шаблонов (открыта с 2B); питается
> per-person presence 3D, но работает и без него (по активности датчиков).

- Модель ритма (статистика/ML.NET поверх event-log; per-zone, где данных хватает), версии в реестре `ml_models`,
  API «спроси ритм» (вероятность состояния в момент T, типичные времена событий) + rhythm/presence-фичи в
  `ContextFeatureJoin`; визуализация «портрет ритма дома» на `/models`.
- **DoD:** ритм обучается на истории и отдаётся по API; хотя бы один потребитель каждого голоса его использует
  (фича тренера, порог «необычности» стража, текст предложения советника); портрет виден в UI.

### Эпик 4J. Страж: субстрат наблюдений + здоровье устройств ⬜

> Второй класс моделей рядом с расписаниями 2I: **временные ряды** (прогноз, скорость изменения, spike/changepoint —
> SSA в ML.NET) + baseline «норма этого устройства в этом контексте». Плюс новая сущность **«наблюдение»** — заметка
> стража: не правило и не предложение; уведомление с объяснением и кнопкой **«это норма — не сообщать»** (кнопка —
> тоже обучающий сигнал). Энерго-аномалии 4D исполняются на этом субстрате.

- **(1) Time-series-шаблоны** в реестре шаблонов 2I (прогноз, rate-of-change, spike/changepoint). **(2) Сущность
  «наблюдение»:** коллекция + лента в UI + «это норма» с подавлением класса наблюдений. **(3) Здоровье сенсоров:**
  «залип»/дрейф/прогноз разряда батарейки (capability `battery` уже копит историю — дешёвый первый детектор,
  стартует эвристиками до полного субстрата). **(4) Энергоподпись устройств:** baseline потребления при данном
  контексте → дрейф («холодильник ест на 30% больше три недели подряд») — совместно с 4D.
- **DoD:** страж присылает первое полезное наблюдение «из коробки» (разряд батарейки/залипший сенсор) с объяснением;
  «это норма» подавляет класс; time-series-шаблон обучается через ml_tasks; энергоподпись ловит синтетическую
  деградацию на тестовой истории.

### Эпик 4K. Погода как ambient-сигнал ⬜

> Единственная «улица» сейчас — солнечная геометрия (2L). Наружная температура и прогноз нужны тепловому автопилоту
> (4L), упреждающему проветриванию и стражу. Идеальный кандидат в плагин 1C: провайдер опционален и онлайн,
> деградация офлайн — принцип 2.

- Погодный плагин (провайдер по выбору) → виртуальное устройство погоды (текущие caps: temperature/humidity/…) +
  **прогноз-контекст** (вперёд-серия, образец `TariffContext` 3C); ambient-фичи в ML (`FeatureLocality` уже
  помечает ambient как всегда-допустимые); офлайн → последние значения + честный статус свежести.
- **DoD:** наружная температура и прогноз доступны правилам/блокам/ML как ambient-сигнал; офлайн-деградация
  штатная; хотя бы одна модель использует погодную фичу с измеримым выигрышем на holdout.

### Эпик 4L. Тепловой автопилот: инерция дома + «цель к моменту» ⬜

> От «уставка сейчас» к «тепло к подъёму»: модель динамики (скорость прогрева/остывания при данной уличной
> температуре) + планировщик, стартующий контур заранее. Требует 4K (погода) и 4I (типичные времена ритма);
> исполнение — штатный слоистый путь (губернатор командует уставкой детерминированного контура под floor-клампами).

- Модель тепловой динамики per-zone на готовой телеметрии; **plan-ahead-актуация** — расширение губернаторов
  («достичь X к моменту T» → расчёт времени старта); стадии Shadow→Bounded→Full и дрейф-демоут наследуются;
  экономия отображается в дайджесте 3J.
- **DoD:** в Shadow планировщик показывает «когда бы я включил и почему»; в Bounded греет к типичному времени
  подъёма под клампами; вмешательства (3J) и точность прогрева видны на карточке модели.

### Эпик 4M. Денежный советник ⬜

> Поверх 3C: прогноз счёта к концу месяца с атрибуцией отклонения; предложения сдвига гибких нагрузок в дешёвые
> часы (апрув → правило/блок `cheap_hours`). Полное NILM-разложение дома по подписи общего счётчика —
> исследовательский трек (Фаза 5); здесь — атрибуция по измеряемым устройствам (3C/Powercalc).

- Прогноз месячного счёта (time-series 4J) + «почему больше обычного» (атрибуция по устройствам/зонам 3C);
  ShiftMiner: повторяющаяся гибкая нагрузка в дорогие часы → предложение расписания/`cheap_hours` с расчётом
  экономии в деньгах.
- **DoD:** прогноз счёта с атрибуцией виден на энергодашборде; предложение сдвига несёт расчёт экономии; апрув
  материализует правило/блок штатным путём.

### Эпик 4N. Лаборатория гипотез и «что-если» ⬜

> Погружение по желанию («исследуй со мной»): математика 2F (MI/χ²/FDR/Granger/η²) получает UI. Вопрос вместо
> конфигурации тренировки.

- **(1) Hypothesis-API + страница:** «влияет ли X на Y (с учётом Z)?» на истории → вердикт со статистикой и
  графиком. **(2) «Что-если» в деньгах:** replay 1F + backtest 2B получают денежную проекцию («если бы управляла
  модель — −X ₽/мес») — честный аргумент на собственных данных для включения автопилотов. **(3) Секвенс-майнинг**
  (PrefixSpan-класс): упорядоченные рутины → сцены/сценарии с порядком шагов (глубже аранжировок 2F×3B).
- **DoD:** пользователь проверяет гипотезу из UI без ML-терминов; денежное «что-если» считается на своей истории;
  секвенс-майнер находит упорядоченную рутину на тестовой истории.

### Снятие UnifiedDeviceService + legacy-канала DeviceStateUpdatedEvent ⬜

После Step 5 сервис выродился: его in-memory реестр write-only (никто не читает), единственная функция —
перекладывать `Envelope<DeviceStateReportV1>` в legacy-событие `DeviceStateUpdatedEvent` для SignalR-релея
ApiGateway. Содержание работы: подписать `ApiGateway.EventRelayService` напрямую на `DeviceStateReportV1`
(StateExchange) → удалить сервис, контейнер из compose, тип `DeviceStateUpdatedEvent` и exchange
`device.events` (с ним — большую часть `Domovoy.Common.Models`). Выигрыш: минус контейнер, минус hop в
hot-path состояния устройств, минус последний legacy-контракт шины. Правка топологии и контрактов → по
правилам «Контракты и совместимость» (`../coding_standards_ru.md`) требует поднять `bus.speaks/understands`, `topology.version` и версии компонентов.
**Отложено до завершения живого прогона Эпика 3K** (решение владельца, 2026-08-07).
