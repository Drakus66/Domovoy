# Стандарты кодирования и паттерны Domovoy

## Обзор

Этот документ определяет стандарты кодирования, паттерны проектирования и лучшие практики, которых следует придерживаться при разработке проекта Domovoy. Последовательное соблюдение этих стандартов обеспечивает качество кода, поддерживаемость и масштабируемость кодовой базы.

## Организация кода

### Структура проекта

- **Структура решения**: Следуйте установленной микросервисной архитектуре с четкими границами
- **Пространства имен**: Используйте `Domovoy.[ИмяСервиса].[Слой]`
- **Ссылки на сборки**: Сервисы должны ссылаться только на общие библиотеки и никогда не ссылаться напрямую друг на друга

### Организация файлов

- Один класс на файл (за исключением небольших связанных классов)
- Файлы должны быть названы в соответствии с основным классом, который они содержат
- Группируйте связанные файлы в соответствующих папках
- Максимальная длина файла должна быть 1000 строк (стремитесь к 300-500)

## Стиль кодирования C#

### Соглашения об именовании

- **Классы, методы, свойства**: PascalCase (например, `DeviceManager`)
- **Приватные поля**: camelCase с префиксом подчеркивания (например, `_deviceRepository`)
- **Локальные переменные и параметры**: camelCase (например, `deviceId`)
- **Константы**: PascalCase (например, `MaxRetryAttempts`)
- **Интерфейсы**: Префикс "I" (например, `IDeviceRepository`)
- **Перечисления**: Имя в единственном числе в PascalCase, элементы в PascalCase

### Форматирование кода

- Используйте 4 пробела для отступов (не табуляцию)
- Используйте `var`, когда тип очевиден
- Используйте явный тип, когда это улучшает читаемость
- Всегда используйте фигурные скобки для управляющих конструкций (if, for, while и т.д.)
- Открывающие скобки на той же строке, закрывающие скобки на новой строке
- Одно выражение на строку
- Ограничивайте длину строки до 120 символов

### Комментарии в коде

- Используйте XML-комментарии для публичных API
- Добавляйте комментарии-описания для классов и публичных методов
- Документируйте параметры и возвращаемые значения
- Избегайте очевидных комментариев, которые не добавляют ценности
- Комментируйте сложные алгоритмы и бизнес-правила

```csharp
/// <summary>
/// Управляет операциями с устройствами, включая регистрацию и обновление состояния
/// </summary>
public class DeviceManager : IDeviceManager
{
    private readonly IDeviceRepository _deviceRepository;
    private readonly IMessageBus _messageBus;
    
    /// <summary>
    /// Инициализирует новый экземпляр DeviceManager

    /// <param name="deviceRepository">Репозиторий для хранения устройств</param>
    /// <param name="messageBus">Шина сообщений для публикации событий</param>
    public DeviceManager(IDeviceRepository deviceRepository, IMessageBus messageBus)
    {
        _deviceRepository = deviceRepository;
        _messageBus = messageBus;
    }
    
    // Методы следуют...
}
```

## Паттерны и принципы проектирования

### Основные принципы

1. **Принципы SOLID**
   - Принцип единственной ответственности
   - Принцип открытости/закрытости
   - Принцип подстановки Лисков
   - Принцип разделения интерфейса
   - Принцип инверсии зависимостей

2. **DRY (Don't Repeat Yourself)**
   - Выделяйте общую функциональность в повторно используемые компоненты
   - Используйте общие библиотеки для сквозных задач

3. **YAGNI (You Aren't Gonna Need It)**
   - Реализуйте функции только когда они действительно нужны
   - Избегайте спекулятивной общности

### Архитектурные паттерны

1. **Внедрение зависимостей**
   - Используйте конструктор для внедрения необходимых зависимостей
   - Регистрируйте сервисы в контейнере DI соответствующим образом (transient, scoped, singleton)
   - Избегайте паттерна Service Locator

2. **Паттерн Repository**
   - Используйте репозитории для абстрагирования доступа к данным
   - Репозитории должны обрабатывать сохранение и извлечение сущностей
   - Возвращайте доменные сущности, а не объекты передачи данных

3. **Паттерн Mediator**
   - Используйте для сложного взаимодействия между сервисами
   - Реализуйте с помощью библиотеки MediatR для паттернов запрос/ответ

4. **CQRS (Command Query Responsibility Segregation)**
   - Разделяйте модели команд (запись) и запросов (чтение) где это уместно
   - Используйте команды для операций, изменяющих состояние
   - Используйте запросы для операций, читающих состояние

5. **Domain-Driven Design**
   - Моделируйте домен точно с помощью сущностей, объектов-значений и агрегатов
   - Определяйте ограниченные контексты, соответствующие микросервисам
   - Используйте доменные события для межсервисного взаимодействия

### Паттерны реализации

1. **Async/Await**
   - Используйте асинхронное программирование для операций ввода-вывода
   - Следуйте асинхронному паттерну на основе Task (TAP)
   - Избегайте смешивания асинхронного и синхронного кода

2. **Паттерн Options**
   - Используйте IOptions<T> для конфигурации
   - Определяйте типизированные классы конфигурации
   - Проверяйте конфигурацию при запуске

3. **Паттерн Factory**
   - Используйте для создания сложных объектов
   - Изолируйте логику создания от бизнес-логики

4. **Паттерн Decorator**
   - Используйте для добавления сквозных задач (логирование, кэширование, валидация)
   - Регистрируйте декораторы в контейнере DI

## Обработка ошибок и логирование

### Обработка исключений

- Используйте исключения для исключительных ситуаций, а не для управления потоком выполнения
- Создавайте пользовательские типы исключений для доменно-специфичных ошибок
- Перехватывайте исключения на границах сервисов
- Никогда не перехватывайте исключения без надлежащей обработки
- Используйте блоки try/catch с конкретными типами исключений

### Логирование

- Используйте структурированное логирование с соответствующими уровнями
- Включайте контекстную информацию в записи логов
- Логируйте на границах сервисов и при важных операциях
- Используйте идентификаторы корреляции для отслеживания запросов между сервисами
- Будьте осторожны с конфиденциальной информацией в логах

```csharp
public async Task<Device> RegisterDeviceAsync(DeviceRegistration registration)
{
    _logger.LogInformation("Регистрация устройства {DeviceId} типа {DeviceType}", 
                          registration.Id, registration.Type);
    
    try
    {
        var device = new Device
        {
            Id = registration.Id,
            Type = registration.Type,
            // Другие свойства
        };
        
        await _deviceRepository.AddAsync(device);
        
        await _messageBus.PublishAsync(new DeviceRegisteredEvent
        {
            DeviceId = device.Id,
            Timestamp = DateTime.UtcNow
        });
        
        return device;
    }
    catch (DuplicateDeviceException ex)
    {
        _logger.LogWarning(ex, "Попытка зарегистрировать дублирующееся устройство {DeviceId}", registration.Id);
        throw;
    }
    catch (Exception ex)
    {
        _logger.LogError(ex, "Не удалось зарегистрировать устройство {DeviceId}", registration.Id);
        throw new DeviceRegistrationException($"Не удалось зарегистрировать устройство: {registration.Id}", ex);
    }
}
```

### Модульное тестирование

- Используйте моки для внешних зависимостей с помощью Moq
- Тестируйте одну концепцию на тестовый метод
- Называйте тесты ясно: [ТестируемыйМетод]_[Сценарий]_[ОжидаемыйРезультат]

### Интеграционное тестирование

- Тестируйте взаимодействие сервисов с внешними системами
- Используйте тестовые контейнеры для зависимостей базы данных и шины сообщений
- Сбрасывайте состояние между тестовыми запусками
- Избегайте тестов с зависимостями от производственных систем

### Покрытие тестами

- Стремитесь к 80% покрытия кода для бизнес-логики
- Фокусируйтесь на критических путях и сложной логике
- Генерируйте отчеты о покрытии как часть CI-процесса

## Рекомендации по производительности и безопасности

### Производительность

- Используйте async/await для операций ввода-вывода

## Зависимости и лицензирование

Domovoy распространяется под **AGPL-3.0-or-later** с опцией **коммерческой dual-license**. Каждая
сторонняя зависимость должна быть совместима с **обоими** путями, поэтому перед добавлением любого
нового пакета NuGet или npm (а также при мажорном обновлении, меняющем лицензию) **сначала проверьте
лицензию и берите только совместимую.**

### Разрешено (пермиссивные — без согласования)

- **MIT, BSD-2-Clause, BSD-3-Clause, ISC, Apache-2.0, Zlib.**
- **MPL-2.0** и другой слабый копилефт на уровне файлов допустимы, но если пакет двойного
  лицензирования (например, `RabbitMQ.Client` — Apache-2.0 / MPL-2.0), **выбирайте наиболее
  пермиссивный вариант** и фиксируйте это.

### Запрещено без явного одобрения владельца

- **Сильный копилефт: GPL-2.0/3.0, LGPL, AGPL.** Копилефт-зависимость вынудит открыть весь продукт
  и **закроет коммерческую лицензию** — это жёсткий стоп, а не предпочтение.
- **Source-available / не-OSI: SSPL, BSL, Elastic License, Commons Clause.**
- **«Этические» лицензии с ограничением использования: Hippocratic License и подобные.** Они
  добавляют ограничения области применения, несовместимые с AGPL и с чистым коммерческим оффером.
  (Именно поэтому `react-leaflet` заменён на `pigeon-maps`.)
- Пакеты **без лицензии / «all rights reserved»**.

### Гигиена

- Избегайте пакетов, занимающих официальный неймспейс (например, не-Microsoft-пакет под id
  `Microsoft.*`), и preview/незаброшенных пакетов в продакшен-путях.
- Сохраняйте атрибуцию: MIT/BSD/Apache требуют сохранения копирайт-уведомлений, поэтому пермиссивные
  зависимости должны попадать в файл `THIRD-PARTY-NOTICES`.
- При сомнении в лицензии определяйте её по репозиторию самого пакета (файл `LICENSE`), а не по
  автодетектору, и фиксируйте решение.

## Контракты и совместимость

Domovoy обновляется **покомпонентно**: обновился один сервис — скачивается и пересоздаётся только
он. Решить, что можно обновить в одиночку, а что тянет за собой соседей, способен только решатель
зависимостей — и доверяет он ровно тому, что объявлено в [`build/components.json`](../../build/components.json).

Отсюда правило: **любое изменение, затрагивающее совместимость, объявляется в том же коммите, что и
само изменение.** Незаявленное изменение контракта — единственный способ тихо получить несовместимое
обновление на боевом доме, и вылавливать это глазами в диффе владелец не обязан.

### Что и когда поднимать

**Шина (`Domovoy.Contracts`).** Ломающее изменение payload или типа сообщения → новый `.vN`-суффикс
в `MessageTypes` **и** поднятие `bus.speaks`/`bus.understands` затронутых компонентов. Обратно
совместимое добавление → только `speaks`. Набор считается совместимым, когда
`max(understands) ≤ min(speaks)`, поэтому поднятый `understands` автоматически заставляет решатель
обновить всех — «полное обновление» здесь не отдельный режим, а вывод.

**HTTP между сервисами** (DbGateway ↔ AutomationService ↔ ApiGateway ↔ служба обновлений):

| Что сделали | Что поднять |
|---|---|
| Добавили эндпоинт или необязательное поле | `provides.<интерфейс>.version` +1 |
| Убрали эндпоинт/поле или изменили семантику | `provides.<интерфейс>.version` +1 **и** `minCompat` = новой версии |
| Начали пользоваться новым эндпоинтом | `requires.<интерфейс>` у потребителя |

Зависимости объявляются **на интерфейс, а не на сервис**: `requires: {"db-api": 5}`, но не
«db-gateway ≥ 4.3». У каждого интерфейса ровно один провайдер, поэтому произвольные циклы в графе
не возникают, а взаимные требования решатель обрабатывает как требование атомарности (обновить
вместе), а не как тупик.

**Топология** (новый сервис, переменная окружения, том, порт, устройство в `docker-compose.yml`) →
поднять `version` в [`build/topology/manifest.json`](../../build/topology/manifest.json) и добавить
`requires.topology` тем компонентам, которым новое поле действительно нужно.

**Изменение обратно совместимо и версий поднимать не надо** — сказать об этом явно (в описании
работы и строкой `Compat: none` в теле коммита). Молчание трактуется как недосмотр.

### Проверки, которые это подпирают

Правило не оставлено на добрую волю:

1. **Снимок публичной поверхности** — `ContractsPublicApiTests` рендерит весь экспортируемый API
   `Domovoy.Contracts` в текстовый снимок и сравнивает с утверждённым. Любая правка payload-record'а,
   типа сообщения или константы роняет тест с диффом. Переутвердить после осознанного изменения:
   `UPDATE_APPROVALS=1 dotnet test --filter ContractsPublicApi`. Файл снимка обязательно появляется
   в диффе — это и есть видимый сигнал, что совместимость требует решения.
2. **`contract-guard`** ([`build/tools/contract-guard.sh`](../../build/tools/contract-guard.sh),
   job в CI) — если диапазон коммитов трогает контрактные пути, а `build/components.json` не менялся,
   сборка падает. Обход ровно один и он громкий: строка `Compat: none` в теле коммита. Аудит дешёвый:
   `git log --grep='^Compat: none'`.
3. **`validate-components`** — набор, который публикуется, проверяется на внутреннюю
   непротиворечивость: интерфейс без провайдера, `requires` вне диапазона провайдера, расхождение по
   версии шины.

Чего эти проверки **не** ловят: семантическое изменение без изменения сигнатуры — тот же эндпоинт,
тот же тип, другой смысл поля. Это остаётся за код-ревью и контрактными тестами.

Подробности пайплайна — [`../ci_cd_ru.md`](../ci_cd_ru.md).
