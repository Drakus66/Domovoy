# Многоуровневая архитектура приложения Domovoy

## Обзор

Domovoy следует современной микросервисной архитектуре с четким разделением задач через многоуровневый дизайн внутри каждого сервиса. Приложение построено на стеке технологий .NET с контейнеризацией Docker и комплексным мониторингом.

## Уровни архитектуры

### 1. Уровень представления
- **API-шлюз** (`Domovoy.ApiGateway`): Служит точкой входа для клиентских приложений, обрабатывая маршрутизацию, агрегацию запросов и сквозные задачи
- **Компоненты UI**: Веб-панель для управления устройствами и мониторинга

### 2. Сервисный уровень
- **Сервис устройств** (`Domovoy.DeviceService`): Управляет регистрацией устройств, состоянием и командами
- **Сервис освещения** (`Domovoy.LightService`): Специализированный сервис для управления освещением
- **Сервис датчиков** (`Domovoy.SensorService`): Управляет различными типами датчиков
- **Сервис обнаружения устройств**: Обрабатывает обнаружение и интеграцию MQTT-устройств

### 3. Доменный уровень
- **Доменные модели**: Основные бизнес-сущности (Устройства, Датчики, Освещение и т.д.)
- **Доменные сервисы**: Инкапсуляция бизнес-логики
- **Доменные события**: Событийная коммуникация для изменений в домене

### 4. Инфраструктурный уровень
- **Шина сообщений** (`Domovoy.MessageBus`): Событийная коммуникация между сервисами с использованием RabbitMQ
- **Шлюз базы данных** (`Domovoy.DbGateway`): Доступ к данным и их хранение
- **Общие утилиты** (`Domovoy.Common`): Общий код и утилиты

### 5. Сквозные задачи
- **Аутентификация и авторизация**: Безопасность пользователей и устройств
- **Логирование и мониторинг**: Структурированное логирование с Loki, метрики с Prometheus
- **Конфигурация**: Централизованное управление конфигурацией

## Взаимодействие между уровнями

- **Взаимодействие сервис-сервис**: В основном через шину сообщений с использованием событий
- **Взаимодействие клиент-сервис**: Через API-шлюз с использованием REST API
- **Взаимодействие устройство-сервис**: Через протокол MQTT для IoT-устройств

## Поток зависимостей

Поток зависимостей следует принципу инверсии зависимостей:

1. Уровень представления → Сервисный уровень → Доменный уровень
2. Инфраструктурный уровень → Доменный уровень
3. Сквозные задачи внедряются там, где необходимо

Это обеспечивает изоляцию доменного уровня и его независимость от внешних зависимостей, в то время как сервисный уровень координирует рабочий процесс приложения.
